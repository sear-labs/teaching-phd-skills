Thanks for being willing to try this.

This is a short exercise using real code from a finished project in the lab — the kind of thing
you would inherit in your first month. It is here so you can see what the work actually looks
like before you commit to anything, and so we can have a better conversation than "tell us
about your research interests."

## What this is, and what it is not

**It is not a test of what you know about energy systems, batteries, or optimization.** The
task is deliberately built so that domain knowledge does not help you. If you find yourself
stuck because you do not know what a term means, that is the task working as intended — look it
up or ask.

**It is not an exam you can fail into a rejection.** [*Jones: state plainly what this does and
does not feed into, and delete this note.*]

What we are actually interested in is how you work when you are handed somebody else's code and
not much explanation, which is most of research.

## The rules

**Four hours. A hard cap.** Not a target, and not a minimum. If you hit four hours with things
unfinished, stop and tell us what you had left — that submission is often more useful to us than
a finished one. If you find yourself at hour six, we set the task badly and we would like to
know.

**Use AI, and tell us how.** Claude, ChatGPT, Copilot, whatever you use. This is not a trap and
there is no purity test — AI-assisted work is how the lab works, and knowing how to check a
model's output is a skill we teach explicitly. What we care about is that you can tell us where
you leaned on it and where you decided not to trust it.

**Ask questions.** [*Name*] will answer clarifying questions while you work. Asking is not a
mark against you. Every question you have to ask tells us something is missing from our
documentation, which is genuinely useful to us.

## What to send back

### 1. Get it running, and reproduce one number

There is a result in the output folder. Reproduce it.

Tell us whether you got the same value. If you got a different one, tell us that instead —
a documented difference is a real finding and we would rather have it than a match you are not
sure about.

### 2. Write the README that would have let you do this in half the time

Assume the reader is you, four hours ago. What did you need to know, in what order, that was
not written down anywhere?

This is the part we will read most closely. It is hard to write one of these without having
genuinely understood what the code does.

### 3. List three things that would break on someone else's machine

Anything — a hard-coded path, an unpinned package, an assumption about where a file lives, a
version that matters. Three is the ask; if you find more, we would like to see them.

### 4. A short note on how you used AI

A paragraph. What you asked it, what it got wrong, what you checked and how.

**Send it as whatever is easiest** — a zip, a repo link, a document. We are not marking the
packaging.

## Afterwards

A 30-minute conversation with [*name*], scheduled whenever suits you. We will ask you to walk
through what the code does, what you tried that did not work, and what you would change about
how the project is organised.

That conversation is the part that matters most, so please do not over-prepare for it. There is
nothing to revise for — we are just going to talk about what you did.

## What we are looking at

No hidden criteria, so here is the actual list:

- Can you get unfamiliar code running without much help
- Can you explain what it does once you have
- Do you notice what is fragile about it
- Can you tell us what did not work, plainly
- Do you know where you checked the AI and where you did not

Things we are **not** looking at: whether you knew the domain, whether it was elegant, whether
you finished.
